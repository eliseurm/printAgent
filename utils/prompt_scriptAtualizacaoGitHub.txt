# Implementação de Build e Release Windows via GitHub Actions

## Objetivo

Atualizar este projeto para que seja possível gerar e publicar automaticamente uma versão Windows do **Print Agent**, contendo tudo o que é necessário para execução.

O usuário final **não deve precisar instalar Java, JRE, JDK, Maven ou qualquer outra dependência**.

Ao final do processo deverá existir no GitHub uma **Release** contendo um instalador Windows `.exe`.

Também deve ser criado o script:

```text
gitHub/scriptAtualizacaoGitHub.sh
```

Esse script será executado manualmente pelo desenvolvedor no Linux e será responsável por:

1. descobrir a versão atual do projeto;
2. incrementar automaticamente a versão;
3. atualizar a versão no `pom.xml`;
4. validar o projeto;
5. criar commit da nova versão;
6. enviar as alterações para o GitHub;
7. criar uma tag Git correspondente à nova versão;
8. enviar a tag para o GitHub;
9. disparar, por consequência, o GitHub Actions;
10. fazer com que o GitHub Actions gere o instalador Windows;
11. publicar o `.exe` em uma GitHub Release.

---

# 1. Regras gerais

Antes de implementar:

* leia a estrutura atual completa do projeto;
* leia o `pom.xml`;
* identifique corretamente o nome final do JAR gerado;
* identifique a branch principal configurada no repositório;
* preserve o funcionamento atual do sistema;
* não altere regras de negócio;
* não altere APIs existentes sem necessidade;
* não remova dependências existentes;
* reutilize a estrutura já existente sempre que possível.

A solução deve funcionar a partir de uma máquina Linux de desenvolvimento, sendo o executável Windows gerado **dentro de um runner Windows do GitHub Actions**.

Não tentar gerar `.exe` Windows localmente no Linux.

O resultado esperado será algo semelhante a:

```text

```

O nome poderá variar ligeiramente caso o `jpackage` determine outro padrão, mas deve sempre ser possível identificar claramente:

* aplicação;
* versão;
* plataforma Windows.

Executar:

```bash

```

# 9. Determinação automática da versão

Não deixar a versão duplicada manualmente dentro do workflow.

O GitHub Actions deve descobrir a versão diretamente do Maven/POM.

Utilizar preferencialmente:

```bash
mvn help:evaluate -Dexpression=project.version -q -DforceStdout
```

Exemplo:

```text
1.0.3
```

A partir dessa informação, determinar o nome do JAR.

Não assumir permanentemente:

```text
print-agent-1.0.2.jar
```

pois a versão será alterada automaticamente.

```text
spring-boot-maven-plugin
```

O resultado esperado é semelhante a:

```text
target/print-agent-1.0.3.jar
```

# 11. Diretório temporário para jpackage

Antes de executar o `jpackage`, criar uma estrutura própria para ele.

```text
build/
├── jpackage-input/
│   └── print-agent-1.0.3.jar
└── installer/
```

Copiar somente os arquivos necessários para:

```text
build/jpackage-input
```

Não passar todo o diretório `target` indiscriminadamente para o `jpackage`.

# 12. WiX Toolset

Verificar o requisito do `jpackage` utilizado no runner Windows para geração de instaladores `.exe`.

Caso necessário, instalar uma versão compatível do WiX Toolset.

Preferir uma implementação previsível e reproduzível.

Não depender silenciosamente de uma versão do WiX eventualmente pré-instalada no runner sem antes verificar sua disponibilidade.

O workflow deve falhar de forma clara caso o ambiente necessário para o `jpackage` não esteja disponível.

# 13. Geração do instalador

Utilizar `jpackage` para criar instalador:

```text
exe
```

A configuração deve seguir conceitualmente:

```powershell
jpackage `
    --type exe `
    --name PrintAgent `
    --app-version "$env:APP_VERSION" `
    --input build\jpackage-input `
    --main-jar "$env:JAR_NAME" `
    --dest build\installer `
    --vendor "Eliseu Engenharia" `
    --description "Print Agent" `
    --win-menu `
    --win-menu-group "Print Agent" `
    --win-shortcut `
    --win-dir-chooser `
    --win-per-user-install
```

Ajuste nomes somente se necessário de acordo com a estrutura real encontrada no projeto.

Não adicionar:

```text
--runtime-image
```

a menos que exista uma necessidade técnica concreta.

O objetivo é permitir que o próprio `jpackage` crie o runtime necessário para distribuir junto com a aplicação.

```text
JAVA_HOME
JDK
JRE
Maven
```

Esse requisito é obrigatório.


```yaml

```

```yaml
permissions:
  contents: write
```

```powershell
gh release create "${{ github.ref_name }}" `

    --verify-tag `
    --generate-notes `

```

```text
gitHub/scriptAtualizacaoGitHub.sh
```

# 18. Incremento automático de versão

Cada execução bem-sucedida de:

```bash
./gitHub/scriptAtualizacaoGitHub.sh
```

deve gerar uma NOVA versão.

Por padrão, incrementar automaticamente o número de **PATCH**.

Exemplo:

```text
Atual:
1.0.2

Nova:
1.0.3
```

Nova execução:

```text
Atual:
1.0.3

Nova:
1.0.4
```

Nova execução:

```text
Atual:
1.0.4

Nova:
1.0.5
```

Considerar versionamento semântico:

```text
MAJOR.MINOR.PATCH
```

Para este script automático, alterar somente:

```text
PATCH
```

Não alterar automaticamente `MAJOR` ou `MINOR`.

---

# 19. Leitura da versão

O script não deve utilizar `grep` frágil diretamente no XML para encontrar a versão se houver uma maneira confiável através do Maven.

Preferir:

```bash
mvn help:evaluate \
    -Dexpression=project.version \
    -q \
    -DforceStdout
```

Exemplo:

```bash
VERSAO_ATUAL="1.0.2"
```

Separar:

```text
MAJOR=1
MINOR=0
PATCH=2
```

e gerar:

```text
NOVA_VERSAO=1.0.3
```

Validar se a versão encontrada segue:

```text
número.número.número
```

antes de continuar.

Caso não siga esse formato, abortar e informar claramente o problema.

---

# 20. Atualização do pom.xml

Preferir utilizar o Maven Versions Plugin, evitando alteração textual insegura do XML.

Exemplo:

```bash
mvn versions:set \
    -DnewVersion="$NOVA_VERSAO" \
    -DgenerateBackupPoms=false
```

Após atualizar, confirmar através do Maven que a nova versão realmente passou a ser:

```text
$NOVA_VERSAO
```

Caso contrário, abortar.

---

# 21. Verificações Git antes de alterar

Antes de atualizar a versão, o script deve confirmar:

### 21.1 Repositório Git

Confirmar que está dentro de um repositório Git.

### 21.2 Branch

Identificar a branch atual.

A publicação deve ocorrer somente a partir da branch principal esperada pelo projeto.

Descobrir a branch principal real do repositório.

Se for:

```text
main
```

exigir `main`.

Não assumir `master` sem verificar.

### 21.3 Working tree

Antes de iniciar, verificar:

```bash
git status --porcelain
```

Se existirem arquivos modificados, não commitados ou não rastreados relevantes, abortar.

Não misturar alterações do desenvolvedor com o commit automático de release.

Informar algo semelhante a:

```text
ERRO: existem alterações locais não commitadas.
Faça commit ou stash antes de gerar uma nova versão.
```

---

# 22. Atualizar referências remotas

Antes de incrementar a versão executar:

```bash
git fetch origin
```

Verificar se a branch local está sincronizada adequadamente com o remoto.

Não criar release sobre uma branch local desatualizada.

Se a branch estiver atrás do remoto, abortar e instruir o usuário a atualizar a branch.

Não executar automaticamente merge complexo.

---

# 23. Verificação de tag

Antes de criar uma nova versão:

```text
v1.0.3
```

verificar se a tag já existe local ou remotamente.

Caso exista, abortar.

Nunca sobrescrever uma tag de release existente.

Nunca utilizar:

```bash
git tag -f
```

Nunca utilizar:

```bash
git push --force
```

---

# 24. Validar o projeto antes da publicação

Depois de alterar a versão no `pom.xml`, mas ANTES de criar commit/tag, executar:

```bash
mvn clean package
```

Se o build ou algum teste falhar:

* abortar;
* não criar tag;
* não fazer push;
* não publicar release.

Como o `pom.xml` terá sido alterado localmente, restaurar a versão anterior automaticamente em caso de falha antes do commit, quando isso puder ser feito com segurança.

O script não deve deixar o projeto silenciosamente em um estado intermediário.

---

# 25. Commit automático da nova versão

Se tudo estiver válido:

```bash
git add pom.xml
```

Criar commit:

```text
Release 1.0.3
```

Exemplo:

```bash
git commit -m "Release $NOVA_VERSAO"
```

Se outros arquivos precisarem legitimamente ser alterados pelo processo de versionamento, adicioná-los explicitamente.

Não utilizar indiscriminadamente:

```bash
git add .
```

dentro do script de atualização.

---

# 26. Push da branch

Enviar o commit:

```bash
git push origin <branch>
```

Confirmar sucesso antes de continuar.

---

# 27. Criar tag

Após o commit ser enviado com sucesso, criar uma tag anotada:

```bash
git tag -a "v$NOVA_VERSAO" \
    -m "Print Agent $NOVA_VERSAO"
```

Exemplo:

```text
v1.0.3
```

---

# 28. Push da tag

Enviar somente a nova tag:

```bash
git push origin "v$NOVA_VERSAO"
```

Não utilizar por padrão:

```bash
git push --tags
```

Isso evita enviar acidentalmente outras tags locais.

O envio dessa tag deverá disparar:

```text
.github/workflows/release-windows.yml
```

---

# 34. Relação entre pom.xml e tag

A versão:

```xml
<version>1.0.3</version>
```

deve gerar:

```text
v1.0.3
```

A GitHub Release deve corresponder à mesma versão.

Não permitir situações como:

```text
pom.xml = 1.0.3
tag     = v1.0.4
```

# 35. Validação no GitHub Actions

No workflow, validar que a versão da tag corresponde à versão do `pom.xml`.

Exemplo:

```text
tag:
v1.0.3

pom:
1.0.3
```

Remover o prefixo:

```text
v
```

da tag e comparar.

Se houver divergência, falhar o workflow.

Isso protege contra criação manual incorreta de tags.

# 44. Testes do script

Antes de considerar concluído, revisar principalmente:

* parsing da versão;
* incremento do PATCH;
* versão `1.0.9` deve virar `1.0.10`;
* versão `1.9.9` deve virar `1.9.10`;
* detecção de working tree suja;
* detecção de branch incorreta;
* detecção de branch desatualizada;
* tag já existente;
* erro no Maven;
* erro no push;
* erro na criação da tag.

Não implementar incremento tratando a versão como número decimal.

Por exemplo:

```text
1.0.9
```

não é um decimal.

Deve ser separado em:

```text
MAJOR=1
MINOR=0
PATCH=9
```

e resultar em:

```text
1.0.10
```

# 45. Ordem transacional desejada

A ordem deve ser:

```text
1. validar ambiente
2. validar Git
3. atualizar referências remotas
4. validar branch
5. validar working tree
6. descobrir versão
7. calcular nova versão
8. verificar tag
9. atualizar pom.xml
10. confirmar nova versão
11. mvn clean package
12. commit
13. push branch
14. criar tag
15. push tag
16. informar sucesso
```

Evitar criar tag antes que o commit tenha sido enviado.

---

# 46. Caso o push da tag falhe

Se:

```text
git push origin vX.Y.Z
```

falhar, informar claramente que:

* o commit da nova versão pode já estar no remoto;
* a Release ainda não foi disparada;
* a tag precisa ser enviada corretamente.

Não tentar resolver utilizando `--force`.
